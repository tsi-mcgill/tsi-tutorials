    Publishing to PyPI: Share Your Package Worldwide

    Building on Python Packages, this tutorial teaches you to publish packages to PyPI so users can install with pip.

    What is PyPI?

    The Python Package Index (PyPI, pronounced "pie-pee-eye") is the official repository for Python packages. It's how pip install numpy works.

    Key facts: - Public and free for open-source packages - Packages are discoverable and searchable - Automatically indexes documentation links - Integrates with GitHub for easy installation

    Preparing Your Package

    Before publishing, ensure your package meets these requirements:

    1. Check Your pyproject.toml

    [project]
name = "my-awesome-package"  # Must be unique on PyPI
version = "0.1.0"            # Semantic versioning
description = "Clear, concise description"
readme = "README.md"
requires-python = ">=3.8"
license = {text = "MIT"}
authors = [{name = "Your Name", email = "your@email.com"}]
keywords = ["astronomy", "statistics"]
classifiers = [
    "Development Status :: 3 - Alpha",
    "Intended Audience :: Science/Research",
    "License :: OSI Approved :: MIT License",
    "Programming Language :: Python :: 3",
    "Programming Language :: Python :: 3.8",
    "Programming Language :: Python :: 3.9",
    "Programming Language :: Python :: 3.10",
    "Programming Language :: Python :: 3.11",
]

    Classifiers

    Classifiers help users find your package. Common ones:

    Development Status :: 3 - Alpha
Development Status :: 4 - Beta
Development Status :: 5 - Production/Stable

Intended Audience :: Developers

    2. Create a License File

    # Download a license from choosealicense.com
# Save as LICENSE (no extension)

    Common licenses: - MIT: Permissive, simple - Apache 2.0: Permissive, includes patent clause - GPL 3.0: Requires derived works to be open-source

    3. Write a Good README

    Your README is shown on PyPI and GitHub:

    # My Awesome Package

Brief one-liner description.

[![Tests](https://github.com/username/my-package/actions/workflows/tests.yml/badge.svg)](...)
[![PyPI](https://img.shields.io/pypi/v/my-package)](...)

## Features

- Feature 1
- Feature 2
- Feature 3

    Create a PyPI Account

    TestPyPI (Recommended First)

    Before publishing to the real PyPI, test with TestPyPI:

    1. Go to test.pypi.org
    2. Sign up
    3. Go to Account Settings
    4. Generate API token
    5. Save token securely

    PyPI (Production)

    1. Go to pypi.org
    2. Sign up
    3. Generate API token (Account Settings)

    Important: Store tokens in ~/.pypirc:

    [distutils]
index-servers =
    testpypi
    pypi

[testpypi]
repository = https://test.pypi.org/legacy/
username = __token__
password = pypi-AgEIc...

[pypi]
repository = https://upload.pypi.org/legacy/
username = __token__
password = pypi-AgEIc...

    Or use environment variables: 

    export TWINE_PASSWORD="pypi-AgEIc..."
export TWINE_USERNAME="__token__"

    Building Your Distribution

    Install Build Tools

    pip install build twine

    Build Distributions

    # Clean previous builds
rm -rf dist/ build/ *.egg-info/

# Build
python -m build

# Verify contents
tar -tzf dist/my-package-0.1.0.tar.gz

    This creates: - dist/my-package-0.1.0.tar.gz (source distribution) - dist/my-package-0.1.0-py3-none-any.whl (wheel)

    Check Metadata

    # Verify package metadata
twine check dist/*

    Should show: Checking distribution for my-package-0.1.0-py3-none-any.whl: PASSED

    Publish to TestPyPI

    # Upload to TestPyPI
twine upload --repository testpypi dist/*

# Or with token in command:
twine upload --repository testpypi --username __token__ --password "pypi-..." dist/*

    Check at test.pypi.org/project/my-package

    Test Installation from TestPyPI

    # Create a test environment
python -m venv test_env
source test_env/bin/activate

# Install from TestPyPI
pip install -i https://test.pypi.org/simple/ my-package

# Try importing
python -c "import my_package; print(my_package.__version__)"

# Cleanup
deactivate
rm -rf test_env/

    Publish to PyPI

    Once you're confident, publish to the real PyPI:

    # Upload to PyPI
twine upload dist/*

# Or directly:
python -m build && twine upload dist/*

    ⚠️ Important: You cannot overwrite versions on PyPI! Always increment version numbers.

    Verify Your Package

    Visit https://pypi.org/project/my-package/

    You should see: - Your package name - README rendered as HTML - Installation instructions - Version history - Classifiers - Links to documentation and repository

    Making Future Releases

    For each new version:

    1. Update version in pyproject.toml: 

      version = "0.2.0"

    2. Update CHANGELOG.md: 

      ## 0.2.0 (2024-01-15)

### Added
- New feature X

### Fixed
- Bug fix Y

### Changed
- API change Z (breaking)

    3. Commit and tag: 

      git add pyproject.toml CHANGELOG.md
git commit -m "Release v0.2.0"
git tag v0.2.0
git push origin main --tags

    4. Build and publish: 

      rm -rf dist/ build/ *.egg-info/
python -m build
twine upload dist/*

    Automating Releases

    GitHub Actions for Auto-Publish

    Create .github/workflows/publish.yml:

    name: Publish to PyPI

on:
  push:
    tags:
      - 'v*'

jobs:
  build-and-publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-python@v4
        with:
          python-version: '3.10'
      - run: pip install build twine
      - run: python -m build
      - uses: pypa/gh-action-pypi-publish@release/v1
        with:
          password: ${{ secrets.PYPI_API_TOKEN }}

    Now pushing a tag automatically publishes:

    git tag v0.2.0
git push origin v0.2.0
# GitHub Actions builds and publishes automatically!

    Managing Versions

    Semantic Versioning (SemVer)

    Version format: MAJOR.MINOR.PATCH[-prerelease][+build]

    • MAJOR (1.0.0): Breaking changes, backwards incompatible
    • MINOR (1.1.0): New features, backwards compatible
    • PATCH (1.0.1): Bug fixes, backwards compatible
    • Pre-release (1.0.0-beta.1): Alpha, beta, release candidate

    Example progression: 

    0.1.0 (initial release)
0.2.0 (new features)
0.2.1 (bug fix)
1.0.0 (stable release)
1.1.0 (new features)

    Handling Version in Code

    Define version in one place:

    # my_package/__init__.py
__version__ = "0.2.0"

    # pyproject.toml
version = "0.2.0"  # Keep synchronized

    Or use dynamic versioning:

    [project]
dynamic = ["version"]

[tool.setuptools.dynamic]
version = {attr = "my_package.__version__"}

    Advanced: Uploading to Other Indices

    Conda-Forge

    For maximum reach, publish to conda-forge:

    1. Create recipe/meta.yaml with build instructions
    2. Create PR at conda-forge/staged-recipes
    3. Conda-Forge maintainers review and merge
    4. Users can install with: conda install -c conda-forge my-package

    GitHub Releases

    Attach distributions to GitHub releases for direct download:

    # Create release with assets
gh release create v0.2.0 dist/*

    Troubleshooting

    "Package already exists"

    You're trying to upload a version that already exists. Increment version and rebuild.

    "Invalid distribution"

    Run twine check dist/* to see metadata errors.

    "Unauthorized"

    Check your API token and username in .pypirc.

    "Repository not found"

    For TestPyPI: use --repository testpypi

    Best Practices

    1. Start with 0.1.0: Reserve 1.0.0 for stable API
    2. Test on TestPyPI first: Always!
    3. Keep CHANGELOG updated: Users need to know what changed
    4. Tag releases: Use git tags for reproducibility
    5. Document dependencies: Be explicit about requirements
    6. Use long_description: GitHub + PyPI usually link
    7. Add CI/CD: Automate testing and releases
